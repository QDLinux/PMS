个人事务后台管理系统 —— 答辩PPT大纲（16页）


第一部分：选题目的与意义（3页）


第1页：封面

  * 项目名称：个人事务后台管理系统
  * 英文名称：Personal Affairs Management System
  * 学生：XXX
  * 指导教师：XXX
  * 日期：2026年6月


第2页：选题背景

  * 个人财务管理需求增长，但市面工具功能割裂——记账、任务管理、目标追踪分散在不同 App 中
  * 传统工具缺乏智能化分析能力，用户面对大量数据"只记不用"
  * 2023年后大语言模型（LLM）技术爆发，为个人助理应用带来新的交互范式
  * 将 AI 大模型与用户真实数据打通，是实现真正"智能助理"的关键挑战

  核心问题：如何让 AI 不再只是聊天，而是能基于用户真实数据提供有价值的分析？


第3页：研究目的与意义

  研究目的：
  * 构建一个集成记账、计划、目标三大场景的统一事务管理平台
  * 探索 LLM Tool Calling 机制在个人数据智能分析中的应用
  * 实现自然语言驱动的数据查询，让用户"说话就能管账"

  研究意义：
  * 理论意义：验证 OpenAI Function Calling 规范在中文场景下对接国产大模型（DeepSeek）的可行性，探索多轮工具调用的工程实践
  * 实践意义：提供一个从"数据记录"到"智能分析"的完整技术方案，降低个人财务管理的认知门槛


第二部分：技术架构设计（4页）


第4页：系统总体架构

  系统采用三层架构 + 独立 AI 服务层：

    第一层：前端 SPA
      框架 Vue 3 + 构建工具 Vite
      组件化开发，使用原生 fetch 通信，SVG 实现数据可视化

    第二层：Spring Boot 3.3.8 后端（Java 17）
      Controller 层共 7 个控制器，对外暴露 30+ REST API
      Service 层共 8 个服务，封装核心业务逻辑
      Repository 层基于 Spring Data JPA，实现数据访问

    第三层：两个外部数据源
      MySQL 数据库：存储用户、记账、计划、目标四类数据
      DeepSeek API：OpenAI 兼容接口，承载 AI 智能对话能力

  架构特点：
  * 前后端分离，Vite 构建产物集成至 Spring Boot 静态资源目录
  * AI 层独立于业务层，通过 AiToolExecutor 桥接真实数据
  * 全系统无状态设计，JWT 实现水平扩展能力


第5页：技术选型

  后端框架    Spring Boot 3.3.8      生态成熟，Java 17 虚拟线程支持
  安全        Spring Security + jjwt  无状态 JWT，HMAC-SHA256 签名
  持久层      Spring Data JPA + MySQL 声明式查询，减少样板代码
  前端        Vue 3 Composition API   组合式 API、响应式数据绑定
  构建        Vite 5                  HMR 热更新、ESBuild 秒级编译
  AI 模型     DeepSeek (deepseek-chat) 国产大模型，原生支持 Function Calling
  HTTP 客户端 java.net.http.HttpClient Java 11+ 内置，零依赖

  为何不用 Vue Router？
  本系统定位为仪表盘单页应用，模块切换通过组件级状态管理实现，引入路由反而增加不必要的复杂度。

  为何纯 fetch 而非 Axios？
  浏览器原生 API，减少一个依赖。"增加依赖要有明确理由"的原则。


第6页：安全架构设计

  JWT 认证全链路（五步串联）：

    步骤1：用户发起登录请求，AuthService 使用 BCrypt 验证密码，签发有效期 24 小时的 JWT Token
    步骤2：前端 http.js 拦截器将 Token 存入 localStorage，随后每个请求自动注入 Authorization Header
    步骤3：JwtAuthenticationFilter 拦截所有请求，验证 Token 签名，解析用户身份
    步骤4：解析后的用户信息注入 Spring SecurityContext，全局可用
    步骤5：CurrentUserService 从 SecurityContext 提取当前用户 ID，所有数据库查询自动携带 owner_id 条件

  安全层次：

    传输层   密码 BCrypt 加盐哈希           防拖库后明文泄露
    认证层   JWT HMAC-SHA256 签名           防 Token 伪造
    授权层   ROLE_USER + owner_id 过滤      行级数据隔离
    会话层   STATELESS 无状态               防 CSRF，支持水平扩展

  安全设计亮点：所有业务查询在 Repository 层强制带 owner_id 条件，即使 Controller 层漏掉校验也不会造成数据越权。


第7页：AI 模块架构设计

  核心挑战：如何让大模型"看见"用户的真实数据？

  解决方案：Tool Calling（即 OpenAI Function Calling 机制），将数据库查询能力封装为 AI 可调用的工具。

  以用户提问"我上个月花了多少钱？"为例，完整执行流程：

    第1步：构建 messages 数组，包含 System Prompt（角色设定与用户数据上下文）和用户消息
    第2步：向 DeepSeek API 发送请求，同时携带 4 个 Tool 的函数定义
    第3步：模型分析后决定调用哪个工具，返回 tool_calls，内容为 get_accounting_monthly_summary，参数 months=1
    第4步：AiToolExecutor 接收工具名称和参数，查询数据库，得到 { monthIncome: 5000, monthExpense: 3200 }
    第5步：将工具执行结果追加到 messages 数组，发起第二轮对话
    第6步：模型基于真实数据生成最终回复："您上月支出 3200 元，收入 5000 元，结余 1800 元"


第三部分：系统设计与实现（6页）


第8页：系统整体设计

  功能模块总览（六大业务模块 + 底层支撑）：

    (1) 记账管理：收支记录 CRUD，支持按日期、类型、分类筛选，提供月度/年度统计视图
    (2) 计划管理：待办事项追踪，三级优先级(HIGH/MEDIUM/LOW)，根据日期自动流转状态
    (3) 目标管理：储蓄进度追踪，目标金额与当前金额实时对比，支持追加进度金额
    (4) 仪表盘：跨模块数据聚合，一页呈现本月收入/支出/结余，计划完成率，目标达成率
    (5) AI 智能助手：自然语言驱动，通过 Tool Calling 查询上述所有模块的真实数据并给出分析
    (6) 账号管理：头像上传、昵称修改、邮箱修改、密码修改

    底层支撑：JWT 无状态认证 + owner_id 行级数据隔离

  前后端三层交互：

    浏览器（Vue 3 SPA）：侧边栏切换 activeSection 驱动组件懒渲染，http.js 统一封装 fetch 请求并自动注入 JWT
    Spring Boot 后端：JwtAuthenticationFilter 拦截验签，CurrentUserService 注入当前用户 ID，统一 ApiResponse 格式返回 { success, message, data }
    MySQL 数据库：4 张表(sys_user / accounting_record / plan_item / goal)，所有 Repository 查询强制带 owner_id 实现行级隔离

  用户操作路径：

    登录后进入仪表盘总览（首页看板，展示本月收支 + 计划/目标环形进度），从侧边栏可切换到以下任一模块：
    - 记账模块：查看账单列表，按日期/类型筛选，新增/编辑/删除记录
    - 规划模块：查看待办事项，按状态/优先级筛选，标记完成
    - 目标模块：查看储蓄进度，追加金额，追踪达成率
    - AI 助手：输入自然语言问题，AI 自动调用 Tool 查询真实数据并返回分析建议
    - 账号设置：修改昵称/密码，上传头像


第9页：实现关键点一 —— 状态自动解析机制

  问题：计划/目标的状态由日期和金额决定，若手动维护极易产生脏数据（如截止日期已过但状态仍为"进行中"）。

  方案：设计 StatusResolver 抽象层，查询时动态计算状态，而非依赖数据库中存储的静态值。

  PlanStatusResolver 判定规则：
    - 开始日期未到        判定为 TODO
    - 在起止日期范围内    判定为 IN_PROGRESS
    - 用户手动标记完成    判定为 DONE
    - 截止日期已过        判定为 ENDED

  GoalStatusResolver 判定规则：
    - 开始日期未到                    判定为 NOT_STARTED
    - 已开始但 currentAmount 未达目标  判定为 ONGOING
    - currentAmount 达到或超过目标      判定为 DONE
    - 用户手动确认达成                 判定为 ACHIEVED
    - 截止日期已过                     判定为 EXPIRED

  效果：状态由规则引擎驱动，数据一致性得到保证；业务逻辑集中在 Resolver，修改规则只需改一处。


第10页：实现关键点二 —— AI System Prompt 工程设计

  System Prompt 不只是角色设定，而是工程化的上下文注入。每次对话前动态构建，包含四个层级：

    第一层·角色定义
      "你是一个个人财务与事务管理助手..."

    第二层·数据上下文（动态注入，每次请求时从数据库实时查询）
      - 本月收入/支出/结余金额
      - 当前待办计划数量
      - 进行中目标及各自进度百分比
      - 最近 5 条账单记录摘要

    第三层·工具使用指南
      - 说明 4 个 Tool 各自的功能和适用场景
      - 约束参数的格式（如日期格式为 yyyy-MM-dd）
      - 引导多 Tool 组合使用的场景（如"分析财务状况"时应同时调用月度汇总、计划查询、目标查询）

    第四层·回答规范
      - 语气专业、简洁、数据驱动
      - 金额始终保留两位小数
      - 必须引用查询到的具体数值，不得给出模糊描述

  设计要点：
  (1) 上下文先行：让模型在回复前已"知道"用户概况，减少不必要的 Tool Call
  (2) 参数约束明确：告诉模型日期格式和月份语义（近N个月），避免无效调用
  (3) 组合引导：明确场景下的多 Tool 调用顺序，如"分析收支"时先查收入汇总、再查支出明细、最后做对比分析


第11页：实现关键点三 —— AI 对话日志与会话管理

  为什么要做对话日志？
  * AI 对话是黑盒过程，没有日志就无法调试和改进
  * 多轮 Tool Calling 的调用链需要可追溯
  * 用户期望对话历史持久化，支持跨会话查询

  三层日志架构（由 AiChatLogService 统一管理）：

    第一层·可读文本日志（文件：username-date.log）
      以时间线格式记录每次对话，便于人工审查，示例内容：
        2026-06-04 14:30:21 | USER: 我上个月花了多少钱？
        2026-06-04 14:30:22 | TOOL: get_accounting_monthly_summary(months=1)
        2026-06-04 14:30:23 | AI: 您上月支出 3200 元...

    第二层·结构化 JSONL 历史（文件：username.jsonl）
      每行一条 JSON 记录，包含 sessionId、role、text、time，支持程序化分析和回溯：
        { "sessionId": "s1", "role": "tool", "text": "...", "time": "2026-06-04T14:30:22" }

    第三层·会话元数据（文件：username-sessions.json）
      记录所有会话的摘要信息，支持前端创建/切换/删除会话：
        [{ "id": "s1", "title": "理财咨询", "createdAt": "2026-06-04" }]

  会话生命周期：创建新会话，多轮对话持续追加记录，前端自由切换会话查看历史，删除废弃会话。


第12页：实现关键点四 —— 前端工程化设计

  组件树结构（无路由、无状态管理库，纯 Vue 3 组件化）：

    App.vue 为根组件，通过 activeSection 状态驱动模块切换，其下挂载 9 个组件：
    - SidebarNav.vue：可折叠侧边栏导航
    - SummarySection.vue：仪表盘首页，收入/支出/结余三张卡片 + 两枚 SVG 环形进度图（计划完成率、目标达成率）
    - AccountingModule.vue：记账模块，内含总览/月度/年度三个子视图
    - PlansModule.vue：计划模块，内含总览/月度/年度三个子视图
    - GoalsModule.vue：目标模块，内含总览/月度/年度三个子视图
    - AiModule.vue：AI 对话界面，支持 Markdown 渲染、多会话管理、三种模式切换（智能对话/理财建议/智能提醒）
    - AccountModule.vue：账号设置，头像上传、昵称/邮箱/密码修改
    - ConfirmDialog.vue：通用确认弹窗，多组件复用

  HTTP 通信层设计（http.js）：
    基于浏览器原生 fetch 封装，统一处理以下横切关注点：
    - 自动注入 Authorization: Bearer <token> 请求头
    - 自动注入 Content-Type: application/json
    - 统一 JSON 解析与错误处理（网络异常、业务异常、Token 过期）
    - Token 过期时自动清除状态并跳转登录页

  设计原则：
  * 零第三方 UI 库，所有组件手写 CSS
  * SVG 环形进度条原生实现，无图表库依赖
  * Markdown 渲染用正则匹配实现，不引入 marked 等第三方库


第13页：AI 模块全流程演示

  场景：用户提问"帮我分析一下最近的财务状况"

  第一轮对话：
    - 用户发送消息
    - 模型分析后判断需要调用 3 个工具：get_accounting_monthly_summary(months=3)、query_goals(status="ONGOING")、query_plans(status="IN_PROGRESS|TODO")
    - AiToolExecutor 并行执行三个查询，分别从 accounting_record、goal、plan_item 三张表中获取真实数据并汇总

  第二轮对话：
    - 将三组工具执行结果追加到 messages 数组，发起第二轮请求
    - 模型基于真实数据生成最终回复，示例：
      "根据您的数据，近三个月情况如下：
       收支：3月结余+1500 / 4月结余-800 / 5月结余+2200
       目标：'买车基金'进度65%，'旅行储蓄'进度30%
       计划：3项进行中，2项即将到期（6月8日前）
       建议：4月超支主因是餐饮消费上涨40%，可设置预算控制"

  Tool Calling 循环控制策略：
  * 最多 5 轮迭代，防止模型反复请求工具导致死循环
  * 每轮检查响应中是否包含 tool_calls，若不含则跳出循环直接返回文本
  * 单次 API 调用设置 30 秒超时保护


第四部分：展望与不足（3页）


第14页：存在的不足

  AI 模块的局限：
  1. 模型依赖单一：目前仅接入 DeepSeek，未做多模型适配对比
  2. System Prompt 可配置性不足：上下文注入内容硬编码在代码中，不支持运营人员动态调整
  3. Token 消耗未监控：没有统计每次对话的 Token 用量和成本
  4. 错误处理不够细腻：Tool Call 返回空数据时，模型的"告知能力"还不够稳定

  工程层面的不足：
  5. 前端单元测试缺失：Vue 组件未覆盖单元测试
  6. CI/CD 流水线未建立：无自动化构建、测试、部署流程
  7. 移动端适配不足：桌面端优先设计，手机端体验欠佳
  8. 异常监控缺失：没有接入 Sentry 等异常追踪，生产问题排查困难
  9. 日志系统简陋：AI 日志用文件系统而非结构化日志框架
